# Security policy

DCS ONLYOFFICE is a demonstrator. It uses fictional data and a fictional security policy, and it is not hardened for production or for real classified information. Vulnerability reports are still welcome, because its design is meant to carry over to real deployments.

## Supported versions

Only the `main` branch receives fixes. There are no releases yet.

## Reporting a vulnerability

**Please do not report security vulnerabilities through public issues, pull requests or comments.**

Report them privately with GitHub's private vulnerability reporting: open the repository's **Security** tab and choose **Report a vulnerability**, or go directly to [the reporting form](https://github.com/linagora/dcs-onlyoffice/security/advisories/new).

Please include as much of the following as you can:

- the component concerned: portal, labelling plugin, policy service, OpenTDF provisioning job, or deployment files and scripts (`deploy/`);
- the commit where you found it;
- a description of the vulnerability and of what an attacker gains;
- the steps to reproduce it, or a proof of concept;
- a suggested fix or mitigation, if you have one.

Never include real credentials, tokens, personal data or protected content in a report: use the fictional accounts and data of the `standalone` stack, and redact the rest.

## What to expect

- We acknowledge your report and keep you informed until the issue is fixed.
- We may ask you for details, and we agree with you on the date of any public disclosure.
- Once the fix is on `main`, we publish a security advisory which, with your agreement, credits you.

## Guidelines for security research

- Use the local `standalone` stack described in the [README](README.md#run-the-stack-locally): it runs the whole stack on your machine, with fictional accounts, a fictional security policy and fictional documents.
- Only test instances that you run yourself, or that you are explicitly allowed to test. Never access or change other people's data, and do not degrade a service: no load or denial-of-service testing.
- Never put real personal data or real protected content into the stack.
- Stop and report as soon as you have shown that a vulnerability exists.

## Scope

In scope: the code and configuration of this repository: the portal, the labelling plugin, the policy service and its OpenTDF provisioning job, and the deployment files and scripts of `deploy/`.

Out of scope:

- vulnerabilities of ONLYOFFICE Docs, OpenTDF, LemonLDAP::NG, Caddy or other dependencies, which belong to their own projects: report them to their maintainers, and tell us as well when they affect this stack;
- the known limitations below, which are properties of the demonstrator, not vulnerabilities.

## Known limitations

These are known properties of the demonstrator, not vulnerabilities:

- Nothing prevents a reader from copying the decrypted text of a portion from the labelling panel into the document body, where it is stored in clear and passes through the Document Server.
- Portion locks coordinate the authors who change portions through the panel; they are not an access control. Anyone able to edit a document can still write a portion's part outside the panel, and the policy service takes the portion label the panel sends for the lock's check. The portal lets only the people who may open a document see or take its locks. Locks live in the policy service's memory: a restart frees them all, and two authors could then change the same portion, the last one's change prevailing. During an editing session, the editor's undo can bring back a portion's earlier envelope and version; the policy service remembers the version a change wrote for a minute only, so that a co-author's editor that has not received the change yet does not change the version before it, and so that an undone change does not keep the portion from changing.
- The window that shows a portion's text next to the cursor relies on plugin window options that ONLYOFFICE Docs does not document (`ShowWindow` with `isTargeted` and `isCustomWindow`), which an end-to-end test checks. To place and close it, the panel receives the keys pressed and the clicks made in the document, and keeps none of them. The editor sees the window's size, which grows with the text, as the envelope's size in the document already shows. ONLYOFFICE Docs 9.4 tells plugins nothing when its File menu opens: in a workbook whose selection is on a placeholder, the window stays over that menu and its print preview, showing its reader only what they may read. ONLYOFFICE has been asked for such an event.
- Unencrypted portions, written before encryption existed, keep their text base64-encoded in the DOCX; they can still be read, but no longer created.
- Portions encrypted before the hybrid key, whose key a static RSA key of earlier versions wrapped, can no longer be read: the KAS no longer holds that key.
- The KAS's private keys are wrapped with a root key kept in `deploy/.env`, not in a hardware security module.
- The plugin runs a build of the OpenTDF web SDK from a fork, which adds hybrid key wrapping until a release of the SDK includes it; [`plugin/vendor/README.md`](plugin/vendor/README.md) gives its commit and how to rebuild it.
- In a workbook, a portion's placeholder is locked by an ONLYOFFICE user protected range that lists no editor: each co-author's editor refuses typing, pasting, cutting, filling, sorting or deleting rows over it, but the lock is an ONLYOFFICE extension, which each browser enforces for its own user, and which Microsoft Excel keeps without enforcing. A co-author can still delete a whole sheet, and with it its portions' ranges, which the next save logs as removed. The panel writes a placeholder before it locks it. To change or delete a portion, it lifts the lock in its own browser only, for the command that writes, outside the editor's history, and to delete one it removes the range, through the editor's internal model, which ONLYOFFICE does not document and a new version may change; it reads the ranges, checks the selected cells and finds the active cell through that model too. The end-to-end tests guard the lift, the lock that comes back after it, and the removal; should a new version refuse to remove a range, the panel writes nothing and the portion stays whole. Anyone able to run commands in the editor could lift the lock the same way. Formulas that reference a placeholder see its marking, never the portion's text, which stays in the envelope.
- While a co-author types in a cell of a workbook, their editor holds back every change that reaches them until they leave the cell, a portion's raise to a label beyond their clearance included: their panel keeps showing the text it showed them until then. What they write stays in their browser as well; a portion change held back for more than the minute the policy service remembers its version would let another author change the same portion, and the workbook would keep both versions. The panel therefore writes nothing into a workbook while its author types in a cell, which it learns through the editor's internal model. In co-editing, the spreadsheet editor's undo takes back an author's command only when it can reverse all of it: a change of a portion's text comes undone, with its earlier envelope and version, while an insertion, a change of label or a deletion stays whole.
- A workbook's page marking sits in its sheets' headers and footers, which the spreadsheet editor shows only when printing, in print preview and in PDF: on screen, the portal's page shows the document label above and below the editor, as the workbook's screen marking. Any author can change or remove the header and footer strings from the editor's dialog, which no lock prevents; the next author's panel to read them writes them again. The panel writes them through the editor's internal model, as it reads the ranges. A left or right section, which the panel keeps as long as the string fits within Microsoft Excel's 255 characters, can run into the centred marking once printed, even a short one when the marking is long and the page narrow: on A4 in portrait, the demo template's sections ran into the marking of a workbook that holds a more restrictive portion, hence a template that prints in landscape. A marking too long to fit within 255 characters on its own, which no label of the demo policy has, is written whole, and Excel may not keep it.
- Protecting existing content protects it from then on only: it went through ONLYOFFICE in clear before, as the panel warns its author before they confirm. The Document Server's working files of the editing session, co-authors' browsers, the stored file until the next save, downloads and other copies made before keep it, and the editor's undo brings it back into the document. In a text document, the panel protects whole paragraphs as plain text: their formatting, list numbering, bookmarks, hyperlinks and unlocked inline content controls go with them. It refuses paragraphs that hold a table, an image or a shape, part of a portion, a page marking or another locked content control, and the comments and notes that it finds through the editor's internal model: a comment whose marks lie inside the paragraphs, which would stay in clear, and a note, which would be lost. A comment that spans them from outside stays, in clear, as do the results that fields elsewhere, such as a table of contents or a cross-reference, last computed from them, until they are updated. The paragraphs leave the document even while changes are tracked, with no tracked deletion that would keep their text; the portion's placeholder then shows as a tracked insertion. In a workbook, the panel protects the cells' displayed values, rows of tab-separated cells, and their formats, data validation and conditional formatting go with them. It refuses cells that hold a comment, which would stay in clear, a formula, whose result depends on other cells, a merge, a portion, a table or a pivot table; other parts of the workbook that copy cell values, such as the cache of a pivot table built elsewhere on them, keep them. The panel reads the cells through the editor's builder API and checks them through its internal model, as for an insertion. In either editor, it compares the content again, in the command that writes, with what it read, and writes nothing if it changed.
- A workbook's screen marking shows, as the page opens, the document label that the stored file names, then each label the panel computes and sends to the page: a label changed since the last save shows once the panel has started, and a page whose panel was closed, or could not compute a label, keeps the last label it received. The label the stored file names at the page's opening is the one the panel last wrote beside the base label, which saves do not compute again: after concurrent changes, it can lag behind the label of the signed binding until a panel writes it again. The page believes messages from its own origin only, which the panel's page shares and the Document Server's frames and other sites do not; any page of the portal's origin could change it, as it could change anything the portal shows. The screen marking writes nothing into the workbook, and Microsoft Excel shows none.
- Anyone able to edit a document can change a portion's label in clear, which the document label, the placeholder in the body and refused readers rely on. Only readers who open the envelope see the label bound to it, with a warning; someone who holds the envelope's key could even replace that bound label.
- The signature of the document label's binding proves that the platform computed the label from the labels in clear, and bound it to the package parts it references, when it stored the file; it proves nothing of who wrote the content. The policy service signs whatever the saved labels in clear give, so a label lowered in the editor is signed too, and logged. The signature covers the parts ADatP-4778.2 lists, and the others that can hold the document's content. In a text document, those are the people who comment (`word/people.xml`), the comments' identifiers and extensible form (`word/commentsIds.xml`, `word/commentsExtensible.xml`), the glossary and its styles (`word/glossary/`), which hold building blocks and the placeholders of content controls, charts with their colours and styles (`word/charts/`) and the shapes drawn on them (`word/drawings/`), SmartArt diagrams (`word/diagrams/`), embedded objects (`word/embeddings/`), ink (`word/ink/`), ActiveX controls (`word/activeX/`) and the thumbnail, a picture of the first page (`docProps/thumbnail.*`). It leaves out the theme, the font table, the settings, the web settings and the numbering definitions, which hold presentation rather than content, though a change to a list's numbering text there would go unnoticed. In a workbook, the signature also covers the parts that can hold its content that Tables 5-2 and 5-3 leave out: threaded comments (`xl/threadedComments/`), which repeat a comment's text, and their authors (`xl/persons/`); drawings and legacy VML drawings (`xl/drawings/`), which place charts, pictures and text boxes on a sheet; SmartArt diagrams (`xl/diagrams/`) and the charts of Excel 2016 (`xl/charts/chartEx<N>.xml`); pivot caches (`xl/pivotCache/`), which copy cell values; tables (`xl/tables/`), slicers and their caches (`xl/slicers/`, `xl/slicerCaches/`); links to other workbooks, with the values they cache (`xl/externalLinks/`); rich values (`xl/richData/`) and cell metadata (`xl/metadata.xml`); chart sheets (`xl/chartsheets/`); queries and their connections (`xl/queryTables/`, `xl/connections.xml`); embedded objects (`xl/embeddings/`), ActiveX and form controls (`xl/activeX/`, `xl/ctrlProps/`) and ink (`xl/ink/`); and the thumbnail (`docProps/thumbnail.*`). It leaves out the theme (`xl/theme/`), the calculation chain (`xl/calcChain.xml`) and printer settings (`xl/printerSettings/`), which hold none. In both formats, the signature also covers the Custom XML parts but the binding's own: the base label's part, and the portions' parts, whose envelopes bind their labels, with their properties parts; every relationship part (`_rels`); and the content types (`[Content_Types].xml`), whose `pack:///` address percent-encodes the brackets a URI cannot hold. A reference to a part that is not XML states the content type the package declares for it, or else the one its extension gives. A part added since signing shows through the relationships or the content types it changes; a part read by its name alone, such as a Custom XML part named as Office names them, shows as a part the signature would reference but does not. A verifier must digest again the package parts that the signature's `Manifest` references: `xmlsec1` reports them but still exits with 0 when one of them no longer matches. A file that the policy service could not sign is stored unsigned, and the failure logged; its binding then references the parts the panel named, those a document of its format saved by ONLYOFFICE always holds, until a save signs it. The demo key, its certificate and the demo authority that issues it, key included, live in `deploy/.env`, not in a hardware security module; a deployment would use a key its PKI certifies, and keep its authority's key away from the stack.
- The sensitivity label that the policy service writes at each save, with a label mapping, is metadata that Office reads and a Microsoft 365 tenant applies its rules to: it encrypts nothing, and says nothing of the protected portions. It follows the document label only, without its informative categories, so a document that holds more restrictive portions carries the sensitivity label of its base label. The binding signature covers it, since it sits in the custom properties part. Editors can delete it in the editor's file information; the next save writes it again. The editor never sees the properties the policy service writes, so the portal sends the stored file's custom properties with each save, to keep the label's date and action id while it stays; when that part exceeds about 6 KB, it sends none and logs it, and the date and the action id then follow the saved file, which holds them as the editing session opened. Word and Excel for the web show it, as a test with a Microsoft 365 tenant found; Word desktop has not been checked. The platform writes no Sensitivity Label Information part (`docMetadata/LabelInfo.xml`), which ONLYOFFICE drops at each save; since Word, in a tenant that enables co-authoring of encrypted files, would show that part's label rather than the signed one, the portal logs a stored file that holds one whenever it serves it, with `Stored file holds a Sensitivity Label Information part`, and serves it all the same. Adding one changes the package's relationships and content types, which the signature covers, so such a file is also logged as changed since signing.
- The portal has the policy service check the signature of every stored file it serves, to the Document Server and for a download, with the certificate the signature carries, which it trusts when one of the configured certificate authorities issued it, the signature was made within its validity, at the signing time it states, and no configured revocation list revokes it; a deployment that configures no authority trusts its signing certificate alone. It logs a file whose signature no longer holds; one signed with a certificate it does not trust, with `The signing certificate is not trusted`, with a revoked one, with `The signing certificate was revoked`, or outside its certificate's validity, with `The signature was made outside its certificate's validity`; one whose binding holds anything its signature does not cover, or whose parts named in the signature's `Manifest` changed since signing, or which holds a part the signature would reference but does not, with the names of those parts; and a file whose binding has no signature, until its next save signs it. A file without labels is not logged: no save signs it. It serves every file all the same: the check shows an alteration after the fact, and never refuses a document. It detects only what the signature covers: a change to the parts it leaves out, such as the theme or the settings, goes unnoticed. A file signed before the signature covered the relationships, the content types and the Custom XML parts is logged, until its next save, with those parts among the parts changed since signing. A signature names the document the portal stores the file as, among its signature properties, and the portal keeps the value of the latest signature it stored for each document: a file whose parts are unchanged is logged when its signature names another document, with `Signed for another document`, or none, as a file signed before signatures named one, with `The signature names no document`, or when it is not the latest the portal stored, with `Not the latest signed version`. The portal keeps that value beside the document's file, in the same storage; a file saved unsigned leaves the earlier value in place. Someone able to rewrite both the file and that value can put an earlier signed version back unnoticed, which a deployment would prevent by keeping the latest signatures apart from the files. A file whose signature alone was removed is logged as unsigned, as a file stored before signing existed; one whose binding and base label were both removed counts as a file without labels. After a change of signing key, the files signed with the previous one still verify when the same authority certified both keys; without authorities, they are logged as signed with a certificate the platform does not trust until their next save, and so are the files signed with the demo's self-signed certificate once a demo authority replaces it. A revocation counts whatever its date: the signing time is the signer's own statement, which a stolen key would make as it pleases, so every file signed with a revoked certificate is logged until its next save. The policy service fetches no revocation list and checks no list's next update: it reads the lists configured when it starts, and a list it cannot read as its authority signed it stops it from starting. A signature carries the signing certificate alone, so the authority that issued it must be configured itself, an intermediate one rather than its root, and a list of the root that revokes that intermediate authority has no effect: a deployment removes the authority from its trust anchors instead. A signing certificate that expires while the policy service runs leaves the files it signs afterwards logged as signed outside its validity; the service does not start with one outside its validity. The trust anchors (`BINDING_TRUST_ANCHORS`) and the revocation lists (`BINDING_REVOCATION_LISTS`) are settings of `deploy/.env`, which a deployment would take from its PKI; to change the demo key, empty `BINDING_SIGNING_KEY` and `BINDING_SIGNING_CERTIFICATE` and run `deploy/scripts/init-env.sh` again, then restart the policy service, as the [hosting guide](docs/hosting.md#configuration) describes.
- The portal checks who opens a document against its saved base label, and decides again for whoever joins its editing session as an editor. The Document Server reports no viewer: someone whose clearance is revoked while a session lasts can still view it live with a configuration signed earlier, and an editor who rejoins sees the document as it is before the portal disconnects them. A base label that excludes someone holding a configuration, or whose holders the portal no longer knows after a restart, ends the session for everyone, viewers included: the Document Server then refuses the earlier configurations, and the document opens again once the session's last save is stored.
- Lowering a base label or a portion label is logged, not prevented: someone able to edit the file outside the panel could still lower it. The journal records these changes: every change of a base label or a portion, every deletion of a portion and every protection of existing content made in the panel, with the person who made it, the labels before and after and, for a portion, its versions; every upload, with the person, the document, the label the file carried, as a base label, and where it came from, whether its binding signature matched, and the base label kept, a lowering marked as such; and every save that lowers a label in clear, a portion's in its part or in its placeholder's tag included, or that removes a portion's placeholder, with the people who held a configuration for the editing session, since the Document Server only names a save's last editor. It never holds a portion's text. It also records every editing session the portal ended, or editor it disconnected, because a base label excludes someone, with the people excluded, and every alert on a stored file served: a file that no longer matches its signature, that holds none, or that holds a Sensitivity Label Information part, with who downloaded it, if anyone did. A change the panel reports while the policy service cannot decide who may open the document is refused and not retried: only the comparison of saves then records it, if it lowers a label. The portal keeps the journal in the stack's database, in a schema that the database setup job owns, through a role that may add entries and read them, never change nor delete them, and names each person by their identifier, name and email address at the time (ADR 0007); administrators read it on a page of the portal reserved to them. A database administrator, or whoever holds the database's superuser password, can still rewrite it. The portal also writes every entry to its log, which Docker keeps as long as the container exists; an entry the database refuses stays there, with the failure. The journal starts with the version that brought it: the entries of earlier versions are in their logs only.
- An upload stores the file as the person sent it, with the platform's parts added: its content in clear stays in clear, in the portal's storage and on the Document Server, as that of any document. The base label is the label the file carries, as its base label part, the document label of its binding or, with a label mapping, the label the mapping pairs with its sensitivity label, unless the person chooses another under the base label rule, and nothing checks it against the content. A sensitivity label is read as [MS-OFFCRYPTO] §2.6.3 reads it, for the mapped tenant only: the tenant's element in the Sensitivity Label Information part decides when there is one, a removed or disabled one meaning no label, and its custom properties otherwise; a sensitivity label the mapping does not know counts as none, and so do several, several elements for the tenant, and one that the mapping pairs with several labels. The upload removes the Sensitivity Label Information part, which the platform never keeps (ADR 0005): a tenant's custom label properties, which its element made stale, go with it, and another tenant's label that only its element held is written as custom properties, without the name Office keeps elsewhere, so that every organisation keeps its label. The label read is only as trustworthy as the file: a base label part or a binding written outside the platform, a lowered one included, is taken as it is. The policy service checks the file's binding signature as it checks a stored file's, and the journal records whether it matched: a binding another tool signed with a certificate the platform does not trust does not match, and neither does a file changed since signing, its base label part included, a file the platform signed before its signature covered every part it covers now, or a signed binding whose document label the file's labels in clear no longer give. A file whose signature does not match is accepted all the same, and signed afresh. A label read that belongs to another security policy, or that the security policy does not define, is refused, whatever base label the person chooses. The policy service reads the portion labels in clear that the file already holds, as at a save, and keeps its portions as they are; the base label and the binding it writes replace any the file carried, and at signing the sensitivity label the label mapping pairs with the document label replaces the tenant's labels in the file. It refuses the files it cannot read, those that Microsoft Purview or a password encrypted among them: the platform decrypts none. An upload whose binding cannot be signed is refused, not stored unsigned. A workbook is read and kept as a text document is, its portions being those whose part and user protected range it holds. The document keeps the format its main part gives, whatever the name says, and the uploaded file's name with that format's extension, which the list shows only to the people who may open it; its identifier, which the portal's log names, is that name reduced to lowercase letters, digits and hyphens.
- The portal's refusal controls who opens a document; the document's content in clear stays in clear in the portal's storage and on the Document Server. The document list shows how many documents a person may not open, and an address tells whether a document exists.
- The panel reads the KAS's "pdp-denied" answer as a decision OpenTDF could not make, shows a technical failure and retries it. OpenTDF 0.27 also gives that answer to evaluation errors it does not classify, which the panel then keeps retrying instead of showing a refusal.
- The Document Server fetches the addresses an editor makes it fetch, private ones included, and signs its requests: the portal's internal route cannot tell a download of the edited document from one an editor provoked.
- The `standalone` profile is for development and isolated demos: it uses a local certificate authority, fictional accounts whose password is their login, and it allows the OAuth password grant for the tests.
- Portal sessions live in memory, and ONLYOFFICE Docs Community Edition keeps editing sessions in memory: a restart signs users out and closes open sessions.

Secrets belong in `deploy/.env`, which Git ignores. Never commit credentials, even revoked ones, or real protected content.
